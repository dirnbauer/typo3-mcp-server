============================
Tool-context A/B benchmark
============================

``mcp:benchmark-tools`` provides a deterministic preflight for the two MCP
costs that are easiest to regress: the fixed ``tools/list`` schema tax and
large tool results that remain in a model's conversation context.

The method follows the useful measurement split demonstrated by
`balatD/typo3-dev-mcp <https://github.com/balatD/typo3-dev-mcp>`__:

- **arm A (full)** serializes every active tool with its unmodified schema
- **arm B (optimized)** serializes the same catalog after the configured
  ``ToolSchemaOptimizer``
- explicit response probes measure complete normalized ``CallToolResult``
  payloads and flag results over the configured byte budget

This command does not claim to replace their multi-run model benchmark. It is
the fast, reproducible layer for detecting schema and response-size regressions
before an expensive task-success experiment.

Run a baseline
==============

The command is dev-site-only. In DDEV:

.. code-block:: bash

   mkdir -p var/reports
   ddev exec vendor/bin/typo3 mcp:benchmark-tools --json \
     --probe='ApplicationInfo={}' \
     --probe='MiddlewareStack={"stack":"frontend"}' \
     --probe='ListEvents={"withListenersOnly":true}' \
     --probe='ContentBlocks={}' \
     --probe='LastError={}' \
     > var/reports/tool-context-baseline.json

Probes are opt-in because they execute the named tool. Use only read-only tools
whose runtime behavior belongs in the measurement. The developer introspection
tools above are read-only and carry MCP ``readOnlyHint`` annotations.

Compare a later change
======================

.. code-block:: bash

   ddev exec vendor/bin/typo3 mcp:benchmark-tools --json \
     --probe='ApplicationInfo={}' \
     --probe='LastError={}' \
     --baseline=var/reports/tool-context-baseline.json

``baselineComparison.optimizedSchemaBytesDelta`` is positive when the published
catalog grew. ``responseBytesDelta`` reports the change for each probe present
in either report. Keep the probe set and fixture state identical when comparing
results.

Thresholds and interpretation
=============================

Useful options:

.. code-block:: text

   --schema-budget=4096
   --response-budget=32768
   --bytes-per-token=2.42
   --probe='ToolName={"argument":"value"}'

The byte counts are exact for the JSON generated by this server. Token counts
are estimates: model tokenizers and MCP host framing differ. The default
``2.42`` bytes/token is deliberately visible and configurable, so reports do
not present it as universal precision.

Read ``tools`` from the top down to find the largest optimized schemas.
``oversizedSchemas`` and ``oversizedResponses`` are threshold failures, not
automatic proof that a tool is badly designed. A large result may be justified
when the caller explicitly asks for full detail; the preferred pattern is a
compact default plus a narrow path/filter or explicit ``full`` option.

For changes that affect agent behavior, follow this deterministic check with
the existing ``composer test:llm`` suite or a paired multi-run task benchmark.
Hold the project state, prompt, model, and ambient tools constant; use several
runs per arm and an oracle independent of MCP.
